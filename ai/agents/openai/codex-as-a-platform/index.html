Codex as a platform: build on the open agent harness

不要把工作迁进一个通用聊天框。让 Codex 进入用户已有的业务界面，在应用给出的上下文、工具与审批边界内完成工作。

一句话结论

Codex 提供执行内核，业务应用提供工作现场

Codex Harness 负责让 Agent 持续理解、行动和反馈；业务应用继续负责用户界面、业务上下文、工具、权限与最终控制。两者结合，才构成面向具体工作的 Agent 产品。

阅读归纳：“执行内核 / 工作现场”用于概括原文的职责关系，不是作者给出的产品术语。

系统怎样工作

从用户正在处理的对象出发，经过调查与审批，再回到业务记录

业务应用界面 · 上下文 · 工具 · 权限 · 记录
Codex状态 · 推理 · 工具交互 · 进度 · 沙箱
人审阅建议 · 批准有后果的动作
为什么不是聊天框

用户理解工作依赖业务视图，而不是一段脱离现场的对话

通用聊天框用户重新描述现场

工作对象、历史记录和可用动作需要被手工搬进对话，原有界面与控制流程被割裂。

→
Agent 进入既有产品界面直接提供现场

用户所选对象、业务数据和审批流程成为 Agent 的上下文，结果仍回到原来的记录系统。

因此，界面不是装饰。它告诉 Agent 用户正在看什么，提供完成任务所需的工具，也给用户留下检查下一步的地方。开放 Harness 的额外价值，是开发者能够检查应用与模型之间的执行层，并按产品需要调整集成。

为什么 Harness 会影响结果：原文引用 ARC-AGI-3 例证——保留推理与上下文压缩使 GPT-5.6 Sol 得分从 13.3% 提升到 38.3%，输出 token 同时减少到原来的六分之一。该结果不能直接外推到所有业务任务。

如何选择接入方式

按产品需要的交互方式和控制程度选择集成层

01

codex exec

适合脚本、CI 任务或一次性后台工作。运行有界的 Agent 工作流，并返回结构化输出。

有界任务 · 非交互
02

Codex SDK

适合应用代码启动、续接或流式接收 Codex 任务，简化常见程序化工作流。

程序化 · 可续接
03

Codex app-server

适合 Agent 成为产品本身的一部分，由应用直接控制会话、事件、中断、工具和审批体验。

产品内嵌 · 直接控制生命周期

这是接入方式的选择，不是能力排名，也不是按任务耗时划分。

Relay 如何验证

示例把总图中的抽象职责，落实到一次运单恢复任务

  1. 工作现场用户在运单看板选择一条异常记录

    点击“比较恢复方案”，而不是从空白提示开始描述全部背景。

  2. Agent 调查应用提供上下文，Codex 通过 MCP 获取最新数据

    Agent 比较选项并说明理由，此时可以保持只读。

  3. 人工控制重新订舱属于有后果的写操作

    未批准则不写入；批准后才允许工具修改底层记录。

  4. 回到现场应用刷新运单视图

    用户从原来的业务界面看到新状态，并决定后续工作。

Relay 使用虚构的种子数据。它验证的是集成模式，不是物流业务效果。

证据与边界

模式已经被采用，但文章没有证明它适用于所有任务

GitHub 与 JetBrains

把 Codex 带入既有 IDE 工作流。

Cisco Cloud Control

在 App Builder 中使用 Codex SDK。

Thrive Holdings 与 Crete

税务准备试点处理 7,000 份申报，并将准备时间缩短约三分之一。

开源范围有限

开放的是 CLI、app-server、SDK 所构成的 Harness 与集成面；模型访问和托管服务仍然分离。

治理仍由产品负责

运行位置、文件与工具权限、审批规则、可观测方式以及记录写入，都需要宿主应用决定。

案例不能直接外推

前两个是采用案例，税务数字来自单个试点；它们不是受控、普遍化的效果证明。

业务规则不能照搬

调查—建议—批准—执行的结构可迁移，但每个场景的权限、风险和记录系统不同。

1. 为什么把 Codex 嵌入业务看板后，应用仍需要提供当前对象、业务上下文和工具？

展开参考答案与对照要点

参考解释：Codex 提供持续推理、维护状态和调用工具的执行循环，应用则知道用户正在处理什么，并掌握业务数据、权限与记录。把两者连接起来，Agent 才能围绕当前工作调查，结果也能回到原界面。

对照要点：是否区分执行循环与业务现场，并说明上下文和结果如何衔接。

容易误解：接入开放 Harness 不等于业务规则自动齐备，也不表示模型访问和托管服务一并开源。

回查：系统怎样工作 · 原文依据（章节：The reusable part is the agent loop；An open harness developers can inspect and adapt；Build software around the workflow）。

2. 在 Relay 示例中，Agent 已比较方案并建议重新订舱，但用户尚未批准。它此时能直接改写运单吗？

展开参考答案与对照要点

参考解释：不能。调查数据、解释建议和改写记录是不同阶段；重新订舱是需要批准的写操作。未批准就保留原记录，批准后才调用应用工具写入，并由应用刷新业务视图。

对照要点：是否保留调查、批准、执行和记录回流之间的边界。

容易误解：建议看起来合理不等于已获批准；读取运营数据也不能被当成写入授权。

回查：Relay 示例 · 原文依据（章节：Example: Relay）。

3. 假设任务只是 CI 中的一次有界后台处理；另一个产品却需要持续会话、中断和审批交互。为什么不应仅按运行时长选同一种接入方式？

展开参考答案与对照要点

参考解释：前者可考虑 codex exec，后者更符合 app-server 对产品生命周期和交互的直接控制。SDK 适合应用代码启动、续接或接收任务流。选择依据是交互方式与控制需求，不能把三者当成耗时档位或能力排名。

对照要点：是否把场景要求对应到集成层，并解释选择理由。

容易误解：不是凡耗时长就必须用 app-server；短任务也可能需要产品内审批。

回查：接入方式 · 原文依据（章节：Choose the right integration layer）。

4. Relay 跑通运单恢复流程，是否就证明相同方案能在真实物流业务中稳定提高效率？

展开参考答案与对照要点

参考解释：不能。Relay 使用虚构种子数据，展示的是上下文、工具、审批和记录回流的集成模式。真实业务的规则、风险和效果仍需验证；其他采用案例或单个试点也不能替所有任务提供效果保证。

对照要点：是否区分集成示例、局部实践和普遍效果证据。

容易误解：无法直接外推不代表模式没有参考价值；应迁移职责关系，而不是照搬业务规则。

回查：证据与边界 · 原文依据（章节：Example: Relay；What developers are building）。

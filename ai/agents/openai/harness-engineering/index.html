Harness 工程：
在 Agent 优先的世界中运用 Codex

Harness engineering: leveraging Codex in an agent-first world

01 / 核心观点

工程师通过设计环境、约束与反馈，让 Agent 逐步承担完整的软件交付。

Ryan Lopopolo · 阅读整理 2026-09-11 · 原文与出处

这篇实践报告讨论：当 Agent 承担代码编写时，工程师如何让它可靠推进任务。这里的 Harness 指围绕 Agent 建设的知识、工具、约束与反馈环境；关注点从逐次指导实现，转向让这些条件持续发挥作用。

本稿保留三类支撑机制及人的职责、环境维护和长期边界，未展开具体目录布局、工具接线和全部实验数据；需要这些细节时，可按文末章节名回到原文。

05 / 自测

自测：我理解了吗？

先用自己的话回答，再按需展开参考答案。重点对照含义和依据，不必逐字一致；你可以理解作者后仍持不同意见。这里不记录成绩或掌握状态。

1. 团队已有很多文档，但 Agent 仍找不到任务依据。为什么继续增加文档数量不一定能解决问题？

展开参考答案与对照要点

参考解释：关键在于知识能否被找到和理解。短入口应连接结构化文档、计划与系统知识，让 Agent 按任务查找；分散或不可访问的信息，即使存在，也未必能参与决策。

对照要点：是否解释了“知识存在”与“任务中可用”的区别，以及入口和组织的作用。

容易误解：不能把这个观点理解成文档越少越好；省略必要知识同样会破坏理解。

回查：知识入口 · 原文依据（章节：We made repository knowledge the system of record；Agent legibility is the goal）。

2. 工程规范已写进文档，Agent 仍引入违规依赖。仅把文档写得更长是否足够？为什么？

展开参考答案与对照要点

参考解释：不够。可查阅的规范还需要变成执行中的检查：发现违规，给出修正反馈，再检查修正结果。文档帮助理解要求，自动检查使要求在实现过程中持续生效。

对照要点：是否串起“要求—发现违规—修正—重查”，而不只是提到自动检查。

容易误解：检查不是替代所有文档或人的判断，也不等于替 Agent 规定每个实现细节。

回查：规则检查 · 原文依据（章节：Enforcing architecture and taste）。

3. 假设 Agent 能读代码和文档，却无法观察运行后的界面、日志或指标。能否仅凭代码修改完成就确认问题已修复？缺少什么？

展开参考答案与对照要点

参考解释：不能据此确认。这个假设场景缺少运行结果的证据，需要让 Agent 获得与问题有关的观察与验证能力；发现偏差后修正，并再次验证。代码改完与结果验证通过是不同的状态。

对照要点：是否指出运行证据的缺口，并解释观察、修正和再次验证的关系。

容易误解：开放日志本身不保证问题已解决；还需要根据结果判断，必要时交由人处理。

回查：观察反馈 · 原文依据（章节：Increasing application legibility；Increasing levels of autonomy）。

4. 能否从本文推出“任何项目只要接入 Agent，就能完全无人干预地交付并长期保持质量”？为什么？

展开参考答案与对照要点

参考解释：不能。本文是特定团队从空仓库出发的实践，自主执行依赖环境、工具和约束投入；人仍负责目标与关键判断，知识和代码需要持续维护，长期效果仍待观察。

对照要点：是否保留环境投入、人的职责和长期未知，而不是把局部实践当成普遍保证。

容易误解：不必因为不能普遍外推就否定这份经验；可以理解其方法，同时保留适用条件。

回查：条件与边界 · 原文依据（章节：We started with an empty git repository；What “agent-generated” actually means；Increasing levels of autonomy；Entropy and garbage collection；What we’re still learning）。

这篇实践报告讨论：当 Agent 承担代码编写时，工程师如何让它可靠推进任务。这里的 Harness 指围绕 Agent 建设的知识、工具、约束与反馈环境；关注点从逐次指导实现，转向让这些条件持续发挥作用。

本稿保留三类支撑机制及人的职责、环境维护和长期边界，未展开具体目录布局、工具接线和全部实验数据；需要这些细节时，可按文末章节名回到原文。

## 核心观点的因果拆解

工程师通过设计环境、约束与反馈，让 Agent 逐步承担完整的软件交付。以下是阅读归纳，不是原文逐字表述。

- **读懂任务**：不知道依据什么做 → 把知识变成可用上下文 → 能理解目标与系统。仓库里的文档、计划与清晰抽象，给任务提供可查找的依据。 对应原文章节 4、5。
- **守住要求**：不知道哪些做法不被允许 → 把要求变成可执行检查 → 能在约束内实现。架构边界与质量要求进入工具，让违规能被发现并纠正。 对应原文章节 6。
- **判断结果**：不知道做完是否正确 → 让结果可观察、可反馈 → 能验证并修正结果。界面、日志与指标提供证据，让实现进入验证与修复循环。 对应原文章节 3、9。

人的工作是定义目标与建设这些机制（章节 02）；三类能力共同支撑实现、验证、修正与交付；持续清理维护这些条件（章节 10）。这不保证所有任务都能自动完成。

阅读顺序：核心观点 → 三个机制及简短论据 → 按机制展开原文实践 → 条件与边界 → 可选自评。保留原文核心章节作为按需查阅的补充。

## 按机制展开原文实践

### 让知识在任务发生时可被使用

- 原文做法（摘要）：短入口连接结构化文档与计划；系统知识需要进入 Agent 能读取和理解的环境。
- 阅读理解：信息有了稳定入口，Agent 才能找到行动依据；清晰的抽象进一步降低理解成本。
- 对应原文章节 04、05

### 让工程要求参与每次执行

- 原文做法（摘要）：用自动检查落实架构边界与质量要求；违规反馈用于修正，随后重新检查。检查约束边界，并不规定所有实现细节。
- 阅读理解：要求成为执行过程中的反馈，才能被反复应用；工程师无需每次重新口头解释。
- 对应原文章节 06

### 让结果成为下一步行动的依据

- 原文做法（摘要）：向 Agent 开放界面、日志和指标，并串起实现、验证、评审与修复。
- 阅读理解：看见结果后才能发现偏差；修正后再次验证，交付过程才能形成闭环。
- 对应原文章节 03、09

## 条件与边界

这是一份特定团队的工程实践报告。人仍负责目标与关键判断，自主程度依赖环境投入；从空仓库出发的实践和高吞吐条件下的交付策略，不能直接推广到所有项目。知识与代码需要持续维护，长期维护效果仍待观察。

### 1. 团队已有很多文档，但 Agent 仍找不到任务依据。为什么继续增加文档数量不一定能解决问题？

<details>
<summary>展开参考答案与对照要点</summary>

**参考解释：**关键在于知识能否被找到和理解。短入口应连接结构化文档、计划与系统知识，让 Agent 按任务查找；分散或不可访问的信息，即使存在，也未必能参与决策。

**对照要点：**是否解释了“知识存在”与“任务中可用”的区别，以及入口和组织的作用。

**容易误解：**不能把这个观点理解成文档越少越好；省略必要知识同样会破坏理解。

### 2. 工程规范已写进文档，Agent 仍引入违规依赖。仅把文档写得更长是否足够？为什么？

<details>
<summary>展开参考答案与对照要点</summary>

**参考解释：**不够。可查阅的规范还需要变成执行中的检查：发现违规，给出修正反馈，再检查修正结果。文档帮助理解要求，自动检查使要求在实现过程中持续生效。

**对照要点：**是否串起“要求—发现违规—修正—重查”，而不只是提到自动检查。

**容易误解：**检查不是替代所有文档或人的判断，也不等于替 Agent 规定每个实现细节。

**回查：**[HTML · 规则检查](./index.html#practice-constrain) · [原文依据](https://openai.com/index/harness-engineering/)（章节：Enforcing architecture and taste）。

</details>

### 3. 假设 Agent 能读代码和文档，却无法观察运行后的界面、日志或指标。能否仅凭代码修改完成就确认问题已修复？缺少什么？

<details>
<summary>展开参考答案与对照要点</summary>

**参考解释：**不能据此确认。这个假设场景缺少运行结果的证据，需要让 Agent 获得与问题有关的观察与验证能力；发现偏差后修正，并再次验证。代码改完与结果验证通过是不同的状态。

**对照要点：**是否指出运行证据的缺口，并解释观察、修正和再次验证的关系。

**容易误解：**开放日志本身不保证问题已解决；还需要根据结果判断，必要时交由人处理。

**回查：**[HTML · 观察反馈](./index.html#practice-verify) · [原文依据](https://openai.com/index/harness-engineering/)（章节：Increasing application legibility；Increasing levels of autonomy）。

</details>

## 01 从空仓库开始

We started with an empty git repository

- 问题：实验从什么条件出发？
- 做法 / 状态：从零构建产品，人工不直接写代码。
- 阅读理解：这是实践背景，不能直接推广为普遍效率结论。

## 02 重新定义工程师角色

Redefining the role of the engineer

- 问题：工程师还负责什么？
- 做法 / 状态：定义目标，补足 Agent 缺失的能力。
- 阅读理解：失败也暴露环境缺口，不只是一次实现错误。

## 03 提高应用的可理解性

Increasing application legibility

- 问题：谁来验证运行结果？
- 做法 / 状态：让 Agent 访问界面、日志和指标。
- 阅读理解：观察能力使自主验证成为可能。

## 04 将仓库知识作为记录中心

We made repository knowledge the system of record

- 问题：知识怎样进入任务？
- 做法 / 状态：用短入口连接结构化文档与计划。
- 阅读理解：上下文需要组织，也需要维护。

## 05 让 Agent 能理解系统

Agent legibility is the goal

- 问题：仅有文档是否足够？
- 做法 / 状态：让系统知识与抽象可被 Agent 理解。
- 阅读理解：可理解性决定它能否有效使用信息。

## 06 落实架构与工程偏好

Enforcing architecture and taste

- 问题：怎样维持代码一致性？
- 做法 / 状态：把边界与质量要求落实为检查规则。
- 阅读理解：人的经验因此能在后续任务中复用。

## 07 吞吐量改变合并理念

Throughput changes the merge philosophy

- 问题：等待与修正如何取舍？
- 做法 / 状态：在高吞吐条件下调整合并策略。
- 阅读理解：这是特定条件下的权衡，不是取消质量要求。

## 08 Agent 生成的完整范围

What “agent-generated” actually means

- 问题：Agent 的工作止于代码吗？
- 做法 / 状态：生成范围覆盖开发配套工作；人仍判断方向。
- 阅读理解：人的参与位置改变，并非消失。

## 09 不断提高自主程度

Increasing levels of autonomy

- 问题：何时能端到端推进？
- 做法 / 状态：串起实现、验证、评审与修复。
- 阅读理解：自主性依赖前面的环境投入。

## 10 熵增与垃圾回收

Entropy and garbage collection

- 问题：坏模式会不会扩散？
- 做法 / 状态：持续清理代码与文档中的退化。
- 阅读理解：一次交付成功不等于长期稳定。

## 11 仍在探索的问题

What we’re still learning

- 问题：哪些结论仍待检验？
- 做法 / 状态：长期维护效果尚未得到充分验证。
- 阅读理解：实践有效与普遍成立之间仍有距离。

## 两个概念模型

经验沉淀：发现问题 → 判断缺口 → 补充机制 → 后续复用。

交付闭环：任务 → 实现 → 验证 → 评审 → 交付；验证或评审发现问题时返回实现，需要人的判断时升级。

pstack 完整指南（第一部分）：验证就是你所需要的一切

The Complete Guide to pstack Pt. 1

真正释放 Agent 规模化能力的，不是再写一层 Prompt，而是让它能控制真实运行环境、观察结果并拿出证据，自己闭合“实现—验证—修正”循环。

验证闭环

Agent 真正的瓶颈，是改完以后仍然需要人替它确认

Lauren Tan 把 verification 定义成一种闭环能力：Agent 不只生成修改，还能操作应用、观察真实结果、收集证据，并在失败时继续修正。这样人从每一步的验证者，变成目标与证据的监督者。

展开作者为什么把 verification 当作基础设施

作者认为，如果 Agent 无法验证自己的工作，人就会持续承担“启动应用、复现问题、点 UI、看日志、确认结果”的工作，Agent 再强也无法真正自主推进。反过来，一旦 Agent 能验证，就可以持续迭代直到满足任务目标，从而让团队成员——包括非工程人员——也能更安全地委托修改。

文章用 Grok Bot 与 Cursor 的实践作为背景，并把 verification skill 描述成比普通 Skill 更接近“critical infrastructure”的能力。

原文依据：Part 1 – Verification is all you need

可复现控制工具

高质量验证不是一页 Markdown，而是一套 Agent 可直接调用的控制面

文章最具体的工程建议是“Build the Lever”：把你手工调试应用时会做的动作，做成稳定 CLI。Agent 不必每次临时写脚本，而是调用一组可组合、可测试、机器可读的命令。

关键变化：工具把“临时推理怎么操作应用”变成“调用稳定接口”。作者认为这能减少 token 消耗，也让验证流程更可复现、更容易测试。

展开 CLI 的设计要求

作者建议优先覆盖 inspection、navigation、interaction、performance、streaming、health/cleanup 等动作；破坏性操作提供 --dry-run，功能用子命令渐进披露，错误信息告诉 Agent 下一步怎么办，帮助文本充分，输出尽量机器可读。

她甚至建议：如果当前技术栈缺少足够好的调试和控制能力，可以为 Agent 专门补工具；在她看来，运行时可调试性会直接影响 Agent 工程的上限。

原文依据：Make it Reproducible；CLI design guidance

Feature Map

控制工具解决“怎么操作”，Feature Map 解决“应该去哪里操作”

当应用越来越大，只给 Agent 一把万能遥控器还不够。作者增加了一层可搜索的 Feature Map：告诉 Agent 有哪些功能、用户如何到达、对应控制命令和常见坑。

为什么维护很重要：应用在变，控制方式和功能入口也会漂移。作者建议至少每天运行一次 /maintain-verification-skill，让 CLI 与 Feature Map 跟上产品变化。

原文依据：Keep agents smart with Feature Maps；Invest in your verification skill

从闭环到规模化

并行和自动化是验证成熟后的结果，不是起点

作者的顺序很明确：先让单个 Agent 能稳定控制并验证应用，再考虑 Cloud Agents、swarm、定时 routines 或自动复现用户反馈。规模化依赖前面的闭环，而不是反过来。

展开作者给出的三个使用例子

新功能：让 Agent 用 verification skill 完成修改，并用视频和截图证明结果。性能：先 trace 当前状态，再做定向优化，最后用 verification + swarm 验证收益。用户反馈：把反馈接入 routines / automations，让 Agent 自动尝试复现；只有验证能力足够可靠时，才进一步考虑自动修复。

原文依据：Cloud Agents；How to use your verification skill

证据与边界

最值得迁移的是“闭合反馈”，不是把作者的规模数字当作普遍结论

文章直接支持的工程判断

真实运行、控制工具、Feature Map 和持续维护可以构成一套更完整的 Agent 验证环境；这些建议有清晰的工程机制与具体实现例子。

文章没有独立证明的效果

“每月 2,000 PR”“100–1000x 团队产出”等是作者对自身实践的报告。正文没有对照组、统一质量指标或失败率数据，不能据此推出所有团队会获得同等增益。

验证的是你定义的检查：工具能运行不等于检查目标就一定正确；错误的断言仍可能得到“通过”。运行时能力决定上限：难启动、难复现、难观测的系统，需要先投入 dev tooling；这本身有建设与维护成本。Feature Map 会过期：它是压缩索引而不是源代码的替代品，因此必须持续与真实产品同步。并行不是免费的：文章强调 Cloud Agents 的便利，但并未系统讨论成本、权限、安全与协调开销。产品依赖要分离：verification-first 是可迁移方法；Cursor Cloud Agents、Automations、Grok Bot routines 是作者当前环境中的具体载体。

因此，可迁移的核心原则是：先让 Agent 能在真实环境里产生可检查证据，再扩大自主性与并发度。

自测

你抓住的是“验证闭环”，还是只记住了工具名？

先回答，再展开参考答案。理解作者不等于接受她所有效果判断。

1. 为什么测试通过仍不等于作者所说的“Agent 已经能验证自己的工作”？

展开参考答案

参考解释：作者要求 Agent 能操作真实应用并观察实际结果。单元测试或静态检查只覆盖预先编码的断言；如果任务涉及 UI、运行时状态、性能或真实交互，还需要启动、复现、操作和收集对应证据。

对照要点：验证是“真实执行 + 观察 + 证据”，而不只是“有测试”。

容易误解：认为增加更多测试文件就自动等于建立完整 verification skill。

回查：验证闭环 · 可复现控制工具 · 原文 Part 1

2. 一个 Agent 已经有能点击 UI 的 CLI，为什么作者还要 Feature Map？

展开参考答案

参考解释：CLI 解决“怎样执行动作”，但大型应用里 Agent 仍要知道“有哪些功能、从用户视角怎么到达、哪个命令控制哪个界面、有哪些例外”。Feature Map 把这些高频探索结果压缩成可搜索索引，减少每次从头建立上下文。

对照要点：工具能力和产品知识是两种不同上下文。

容易误解：把 Feature Map 当成代码之外的第二份永久真相；作者反而强调它必须持续维护。

回查：Feature Map · 原文 Feature Maps

3. 如果验证脚本本身检查错了条件，能否仅凭“Agent 自己跑过验证”确认修改正确？

展开参考答案

参考解释：不能。verification skill 解决的是让 Agent 有能力执行检查并根据反馈迭代，但检查本身仍可能设计错误。文章强调的是把反馈闭环做成基础设施，不是证明任何自动检查天然可靠。

对照要点：“能验证”与“验证目标正确”要分开。

容易误解：把 verification-first 理解成只要验证步骤自动化，人就不再需要设计边界和审查证据。

回查：证据与边界

4. 为什么作者把 Cloud Agents 和自动修复放在建立 verification skill 之后？

展开参考答案

参考解释：并行只会放大已有能力。如果单个 Agent 还不能稳定启动应用、控制功能和判断结果，那么同时运行更多 Agent 只会增加需要人兜底的失败。先把单 Agent 的反馈闭环做稳，才有条件把相同能力复制到隔离并行环境和自动触发任务。

对照要点：先闭环，再复制闭环。

容易误解：把“更多 Agent”本身当作吞吐量提升的充分条件。

回查：从闭环到规模化 · 原文 Cloud Agents / Automations

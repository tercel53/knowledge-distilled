Claude Code Harness Engineering：五层 Harness 与渐进建设路径

Claude Code Harness Engineering: The Complete Guide

把生产可靠性拆成五种不同问题，再按失败模式渐进补齐；不要把 Harness 简化成一份更长的 CLAUDE.md。

本文本身是导航型教程，不是受控实验或完整生产规范。下面优先恢复五层之间的职责差异、建议与强制的区别，以及证据能支持到哪里。

五层职责

五层不是五份配置，而是五种不同的可靠性问题

文章把 Harness 定义为模型之外的运行系统。Memory 提供上下文，Tools 扩展能力，Permissions 收窄授权，Hooks 进入工具调用路径实施约束，Observability 为诊断与验证留下证据。

建议与强制

最重要的变化，是从“告诉模型”走向“在执行路径上约束模型”

`CLAUDE.md` 中的规则仍属于模型要理解和遵循的信息；PreToolUse hook 则可以在工具执行前检查并阻断动作。危险操作因此不应只靠文字提醒。

这是本文对 Claude Code Harness 的实践归纳。具体 permission / hook 语义会随产品版本变化，实施时仍应回到官方文档核对。

这条实践顺序不同于五层编号。它表达的是“guardrails before capabilities”的风险控制思路，而不是说 Hooks 在架构上属于第二层。

证据边界

+13.7 说明 Harness 会影响结果，不证明五层模型各自贡献

文章引用 LangChain 在 Terminal Bench 2.0 上从 52.8% 到 66.5% 的提升，但原案例包含 context injection、self-verification、compute allocation 等多项改动。这个结果可以支持“同一模型下 Harness 设计很重要”，不能推出“配置齐五层就必然提升 13.7 分”。

文章还把 OpenAI Codex、Ghostty 和开发者调查并列为“constraints beat capability”的证据。它们的来源、任务与评价口径不同，更适合作为实践动机，不应包装成三组同口径实验共同证明普遍因果。

本文明确称自己是 navigation hub / reading path，而且当时 Tools 与 Permissions 甚至没有独立 deep-dive，因此它适合做导航框架，不是完整生产配置规范。

1. 为什么已有 CLAUDE.md 仍不等于完整 Harness？

因为它主要解决 Memory / 上下文问题，不能替代工具范围、权限、运行时阻断和事后观测。

展开参考答案

展开参考答案

不能直接证明。它说明 Harness 改动可以影响同一模型表现，但不能把增益归因给本文五层中的某一层或“装齐五层”。

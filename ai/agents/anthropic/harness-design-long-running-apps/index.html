Harness 设计

Harness design for long-running application development

将规划、生成和评估分开；先约定怎样才算完成，再让评估者像用户一样操作运行中的应用，形成反馈闭环。模型升级后，还要逐项移除 Harness 组件，验证哪些仍有必要。

核心结论

Harness 的价值，在于把不可靠环节纳入可检查的反馈闭环

长时自主编码不应由同一个 Agent 一路生成并自我验收。Planner 把简短需求扩展成完整的产品方案文档，Generator 负责实现，Evaluator 则像用户一样操作运行中的应用，按照预先约定的标准验收并反馈问题，由此推动下一轮修复或调整方向。

问题诊断

只让一个 Agent 长时间运行，会同时削弱连贯性和判断力

A

上下文越长，执行越容易漂移

随着上下文不断累积，模型可能逐渐失去连贯性；Sonnet 4.5 甚至会在认为自己接近上下文上限时提前结束工作。清空上下文，再由结构化交接文件把必要状态传给新的 Agent，可以让后续工作从干净的上下文继续。

上下文累积→结构化交接→新会话继续
代价：编排复杂度、token 与延迟上升；交接文件必须保留足够状态。
B

让同一个 Agent 生成并自评，容易高估结果

同一个 Agent 往往会宽容地评价自己的成果；这一倾向在主观设计中最明显，在结果可验证的软件任务中也会出现。将生成和评估交给不同 Agent，更容易单独把评估者调校得严格。

生成≠独立评估→可执行反馈
分离本身并不自动带来严格判断，评估者仍需标准、示例与持续校准。

让主观质量可以评估

把抽象的“好不好”拆成具体的评估标准

作者先在前端设计上验证这一思路：美感不能被一个分数完全概括，但可以把设计原则和个人偏好写成清晰的评估标准，再由评估者操作真实页面并逐项指出问题。

展开实验观察与限制

完整运行最长约四小时。即使在第一轮，明确标准也能让结果优于没有额外提示的基线；后续反馈通常会让设计更鲜明。在荷兰艺术博物馆案例中，第十轮从常规落地页转变为空间化的 3D 画廊体验。

但作者有时更喜欢中间轮次，方案复杂度也会随迭代上升。“museum quality”一类措辞还会让设计趋向特定风格，说明评分并不是客观、中立的审美尺度。

扩展到全栈编码

产品方案确定方向，编码前约定完成标准，实际操作负责验收

术语说明：原文的 product spec 指包含产品背景、功能范围、用户故事和总体技术方案的完整方案文档；sprint contract 指 Generator 与 Evaluator 在编码前共同确认的本轮验收约定。

为什么 Planner 不应提前写死实现细节？

作者担心前期写错技术细节会影响后续实现，因此让 Planner 聚焦产品背景、功能范围和总体技术方案，把具体实现路径留给后续工作。Generator 将工作拆成较小的功能块，Evaluator 则从功能范围与实现深度、功能可用性、视觉设计和代码质量四个方面设定最低通过线。

Solo20 min · $9游戏模式无法正常操作

完整 Harness 的成本超过单 Agent 方案的 20 倍。Evaluator 能准确定位拖拽填充、删除条件和 API 路由顺序等缺陷；但操作流程不清楚、物理碰撞异常和关卡无法通过等问题仍然存在。

Generator 连续工作两小时以上；QA 仍发现录音只是占位功能、片段不能拖动、缩放或切分、效果器缺少可视化编辑等核心缺口。最终应用已经具备编排、混音、播放和 Agent 工具调用，但离专业级 DAW 仍有很大距离。

证据性质：这是作者对少量构建案例的经验报告，不是受控基准。成本与结果受模型、提示、应用类型和验收标准影响，不能外推为固定收益。

随模型能力演化

模型升级后，要重新验证每个 Harness 组件

任务位于模型的可靠范围内评估者带来的价值可能低于成本 任务接近或超出可靠边界独立评估仍能发现关键缺口

作者没有一次性大幅修改 Harness，而是先阅读真实运行记录，找出模型判断与人工判断的分歧；然后一次只移除一个组件，观察最终结果，避免误判性能变化的原因。

条件与边界

独立评估能改善判断，但不能保证验收可靠

评估者也会放宽标准

早期 QA 会先找到真实问题，又说服自己问题并不严重，最后仍然放行；测试也常停留在表面。作者通过阅读日志、寻找判断分歧和修改提示，经过数轮才把评估者校准到可接受的水平。

达到最低通过线不等于测试充分

最终应用仍有布局瑕疵、不自然的交互和未经测试的深层 bug。评估只能覆盖它实际探索过、且评估标准明确要求检查的部分。

可观测信号限制了评估范围

在 DAW 案例中，Claude 无法真正听见音乐，因此很难评价音乐品味；Playwright 擅长检查可操作界面，但不能自动覆盖听觉等其他现实信号。

复杂度必须靠增益证明

Planner、Evaluator、重置与 Sprint 都增加成本。是否保留，取决于当前模型在当前任务上的可靠边界，而不是架构潮流。

## 图解首遍：过程记录

### 桌面 1365×900

- 标题首屏：标题直接列出“写入、选择、压缩与隔离”，摘要将它们改写为“保存、读入、缩短、不共享”。我在看到主图前已经能把四个词与四类动作做初步对应。
- 主图：桌面一屏能同时看到四张卡片以及底部两条辨析。中心是“有限上下文窗口”，下方四张卡片并排成 2×2；因此我把它读成围绕同一资源问题的四个并列动作，不是先写入、再选择、再压缩、最后隔离的流程。
- 写入、选择、压缩三张卡片都用单向箭头：当前窗口→外部状态、外部资料→当前窗口、较长内容→较短表示。箭头方向具体解释了信息向外保存、向内取用、在窗口内变短。
- 隔离卡片不同：上方“共享上下文”通过一条竖线接到横向分叉，再分别向下指向“窗口 A”和“窗口 B”。几何上是一个来源分成两个终点；A 与 B 之间没有箭头，页面也没有显示 A 在前、B 在后的序号。因此我首遍读成“共享上下文分别分到 A/B 两个独立边界”，不是“A→B 串联”。卡片标题“让不同任务不共享全部内容”和邻近说明“使用独立窗口……”强化了这个读法。
- 图底部的“写入≠压缩”“选择≠隔离”替我排除了两个容易混淆的近义关系：保存到外部不同于把当前内容变短；控制读入不同于划定不共享边界。

## 首遍自由复述（冻结）

这篇笔记讲的是如何管理 Codex CLI 每一步真正能看到的有限信息。它把做法分成四类：把以后还要用的状态写到窗口外；到需要时只选择相关资料读进来；把过长内容压成较短表示；把不同任务分到不必共享全部内容的独立窗口和边界。四类动作是并列且按需要使用的，不是固定顺序。隔离图表示一份原本共享的上下文被分到窗口 A 与窗口 B 两个分支，而不是信息从 A 再流向 B。

## 首遍五问（冻结）

1. **它讨论什么问题？** 讨论 Codex CLI 的有限上下文应该怎样保存、取用、缩短和分隔，避免需要的信息丢失、无关信息占位或不同任务互相干扰。
2. **主要结论是什么？** 不要把上下文工程理解成不断塞入更多信息；应按任务使用写入、选择、压缩、隔离四种不同操作，而且不能把相近的操作混为一谈。
3. **为什么可能有效，各部分如何联系？** 图中三种箭头分别改变信息的去向或长度，隔离则把共享范围分叉成两个边界。我的理解是它们针对不同问题：写入处理会话外保留，选择处理当前相关性，压缩处理占用，隔离处理串扰。四者围绕同一个有限窗口互补，但首遍图只展示机制直觉，没有展示效果验证。
4. **它提供了什么依据？** 首遍范围内只有作者整理出的信息流示意、短说明和“不是原文图表”的声明；没有看到实验设计、数据或可复核案例。因此首遍只能说图解释了概念，不能说它证明了效果。
5. **适用条件、代价或限制？** 首遍明确读到：配置会随版本变化；这是观点/实践综述而非普遍有效的受控实验；四种操作都不是正确性的充分条件。图里还提示隔离涉及窗口、工具范围、权限和操作系统沙箱，但首遍尚不清楚这些边界是否等价、各自代价多大。

## 全文第二遍：新增理解与负担

第二遍按页面顺序阅读了“信息流”“组合效应”“证据边界”“自测”和“来源”。参考答案在本节记录完成前保持折叠。

### 信息流

- 写入的具体落点是 `AGENTS.md / memories / PLANS.md` 等可再读状态。它解决的是会话历史易失与跨压缩、跨会话恢复的问题，但外部状态也可能过时。这使首遍的“写到外部”从方向图变成了可操作的机制与代价。
- 选择通过 Tool Search、MCP 工具范围和 Web Search 等方式控制当前读入哪些工具定义或资料。正文第一次明确说明选择同时涉及相关性和读入时机。
- 压缩包含较早历史摘要、schema 压缩和预算收尾交接。正文强调“变短”不等于无损，摘要可能漏掉精确约定；因此关键状态仍适合写入可复核文件。这把写入与压缩的组合关系讲清楚了。
- 隔离在正文中被拆成三个层次：Subagents 分开会话历史，profiles 限定能力，OS sandbox 限制资源访问；三者不是同一种安全保证。这里补足了首遍主图没有表达的关键边界：独立上下文只解决会话串扰，不自动等于工具、权限和文件访问都安全隔离。它还明确写出协调与交接成本，简单任务未必值得拆分。

### 组合效应

- 四个动作按任务需要触发，不是固定路径；每个单独处理一种风险，组合才形成系统。
- 写入×选择：完整知识保存在外，需要时只取相关部分；写入×压缩：摘要后仍能从计划或记忆恢复关键状态；选择×隔离：每个子任务只暴露自己的工具和资料；压缩×隔离：各窗口分别压缩，避免一项任务的摘要覆盖另一项。
- 页面还区分提示工程、上下文工程和 Harness 工程：前者优化一次请求的表达；上下文工程管理推理能看到什么；Harness 工程借助权限、沙箱、事件钩子和多代理协调让这些决策持续发生。这个层级关系是首遍图没有提供的新理解。

### 证据边界

- 可由官方资料核对的是 Codex 的具体能力是否存在，例如 `AGENTS.md` 层级、memories、自动压缩、子代理和工具范围。把这些能力归到四策略，则是文章作者的分析映射。
- 85–98%、100,000 tokens、30,000–40,000 等数字缺少统一任务、模型、团队和评价方法，只能当风险提示，不能当普遍切换阈值。
- “超过两个领域就使用 subagents”“每个里程碑更新 PLANS.md”也是实践清单，不是 Codex 的必备条件；实际采用要权衡任务耦合度、协调成本、模型与工具负载。

### 阅读负担与理解变化

- 四策略本身经主图已经能复述；全文主要补上具体 Codex 映射、组合方式、成本和证据等级，而不是推翻首遍框架。
- `schema`、MCP、profiles、OS sandbox 等名词密集出现。页面通常能说明它们在信息流中的作用，但若读者完全没接触过 Codex，只能获得“用于缩短工具定义/限定能力/限制资源”的功能性理解，不能据此掌握配置方法；这是主题复杂度和本页主动省略配置片段共同造成的范围限制。
- 组合章节四张配对卡片很短，具体说明了两两互补，不需要自行补很多因果。相比之下，Harness 工程一句同时列出权限、沙箱、事件钩子、多代理协调，需要回看前面的隔离层次才能理解它与上下文工程的区别。
- 隔离的全文解释没有改变首遍对几何关系的判断：仍是子任务进入独立会话，再分别施加工具/权限/文件边界，而不是 A→B 传递。不过全文澄清了“独立会话”只是隔离的一层，不能把分叉图过度理解成完整安全保证。

## 自测原始回答（参考答案展开前冻结）

1. **为什么把完整 MCP 工具目录写进 AGENTS.md，不能同时替代“写入”和“选择”？** 把目录写进文件只完成了外部保存；若每轮把完整目录都装入上下文，仍没有根据当前任务筛掉无关工具定义。写入回答“存在哪里以便以后读”，选择回答“此刻读哪些、什么时候读”，两者不能互相替代。
2. **自动压缩已经存在，为什么多文件长任务仍可能需要外部计划文件？** 自动压缩把旧内容变短，可能丢掉精确约定、未完成步骤和当前状态。外部计划文件是可复核、可重新读取的持久状态，在压缩或跨会话之后可以帮助恢复；但它也需要维护，可能过时。
3. **子代理拥有独立上下文，是否等于它已经获得安全隔离？** 不等于。独立上下文只分开会话历史；安全隔离还涉及可用工具、权限和操作系统/文件资源边界。这些层次应分别配置与判断。
4. **能否把 30,000–40,000 与 100,000 token 当作自己项目的可靠切换阈值？** 不能直接照搬。这些数字缺少统一任务、模型、团队和评价方法，应当只作为可能退化的风险提示；自己的项目需要基于实际负载和评价方法测试。

## 展开参考答案后的补充

在上述四题答案落盘后，我展开了四个“参考答案与对照要点”，再逐题对照：

1. 我的回答与参考解释一致。参考答案额外把容易误解处说得更精确：选择不是删除完整目录，而是控制它进入窗口的时机与范围；窗口成本来自无关内容也被当前载入。
2. 我的回答覆盖了压缩有损、外部计划可重读和计划会过时三点。参考答案补出了更明确的组合表述：“写入 + 压缩”共同形成恢复路径，而不是把计划文件当成自动正确的永久记忆。
3. 我的回答与参考解释一致。参考答案进一步给出一个具体不可推断项：用了 subagent 也不能据此断定它无法访问不相关文件或工具，因为这取决于工具范围、profile 和 OS sandbox 的配置。这与主图“共享上下文→窗口 A/B”的关系并不冲突，而是限制了读者对分叉图能推出的安全结论。
4. 我的回答与参考解释一致。参考答案补充了重要区分：数字证据弱限制的是“效果强度有多确定”，不等于四策略框架本身无用。

## 全文后的五问更新（不回写首遍）

1. **它讨论什么问题？** 如何围绕 Codex CLI 的有限上下文持续做保存、按需读入、缩短表示与任务分界，并把这些策略落实到具体机制。
2. **主要结论是什么？** 写入、选择、压缩、隔离是四类互补的信息操作，应按任务组合使用；它们不是固定流程，也不保证正确。独立上下文、能力约束和资源访问控制必须分开理解。
3. **为什么可能有效，各部分如何联系？** 写入提供跨压缩/跨会话的可恢复状态；选择减少当前无关负载；压缩换取更短表示；隔离减少任务串扰并可继续叠加能力与资源边界。写入能补压缩的有损，选择能与隔离一起缩小各子任务暴露范围，各隔离窗口又可独立压缩。
4. **它提供了什么依据？** 页面把可在 OpenAI Docs 核对的 Codex 机制，与作者将这些机制归入四策略的分析映射分开；还列出原文和三项官方文档作为回查入口。我没有打开这些外部链接，因此这里只记录页面所述的依据结构，没有独立核验来源。
5. **适用条件、代价或限制？** 外部状态会过时，压缩可能丢精确约定，隔离有协调和交接成本，简单任务未必值得拆分；配置随版本变化。文章中的百分比、token 数和“超过两个领域”等清单缺少足以普遍外推的统一条件，项目应按模型、任务、工具负载、耦合度和质量评价实测。

### 第一遍自由复述

这篇笔记把 Codex CLI 的上下文工程归纳成四种信息运动。当前窗口容量有限，因此不应让所有东西一直挤在里面：需要长期保留的状态可以写到外部；进行下一步时再从外部资料中挑选相关内容；窗口内已经太长的表示可以压缩；彼此不同的任务则可以拆进不同窗口或能力边界，避免互相干扰。这四种动作分别处理遗失、噪声和串扰问题，可以组合使用，但它们本身不能保证推理一定正确。

其中两组区别最重要：写入是在改变信息的存放位置，压缩是在缩短当前表达；选择是在决定这一次读入什么，隔离是在决定哪些内容或能力不共享。第一遍还不能说明具体机制如何组合、效果依据有多强，也不能把“隔离”直接理解为完整的安全保证。

### 第一遍五问

1. **它讨论什么问题？**
   - 讨论 Codex CLI 在有限上下文窗口中怎样管理信息，使下一步推理看到需要的内容，同时减少遗漏、噪声和不同任务之间的串扰。

3. **压缩明确是可能有损的表示缩短。**
   - 自动上下文压缩用于摘要较早历史，schema 压缩减少工具定义占用，预算收尾提示用于留下当前状态。

## 自测原始回答（参考答案仍折叠）

### 1. 为什么把完整 MCP 工具目录写进 AGENTS.md，不能同时替代“写入”和“选择”？

我的回答：写进 AGENTS.md 只完成了把工具目录保存到外部、让后续可读取，也就是“写入”。“选择”要求当前任务只加载相关工具定义，并控制加载时机；如果每轮都把完整目录带进窗口，反而没有降低无关定义占用，不能替代按需筛选。

### 2. 自动压缩已经存在，为什么多文件长任务仍可能需要外部计划文件？

我的回答：自动压缩会把较早历史摘要成更短表示，可能漏掉精确约定、进度或下一步。外部计划文件把关键状态保存在可复核、可再读的位置，即使会话被压缩或跨会话，也能恢复。它和压缩互补，而不是重复。

### 3. 子代理拥有独立上下文，是否等于它已经获得安全隔离？

我的回答：不等于。独立上下文只把会话历史分开；可访问哪些工具、权限和文件，还要由 profiles、权限配置和 OS sandbox 等边界控制，而且这些层次提供的保证不同。

### 4. 能否把文章的 30,000–40,000 与 100,000 token 数字当作自己项目的可靠切换阈值？

我的回答：不能。这些数字缺少统一的任务、模型、团队和评价方法，只能提醒长上下文可能退化。自己的项目应结合任务耦合度、协调成本、模型与工具负载实测后决定切换点。

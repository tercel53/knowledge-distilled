### 原文主要主张

1. **编码代理的主要瓶颈已从单次提示措辞转向信息供给。** 作者以“80% problem”为开篇依据：代理会完成当前窗口中可见的部分，却漏掉窗口外的文件和事实；这被界定为上下文供应问题，而非单纯的提示词问题。
2. **行业实践经历 Prompt Engineering → Context Engineering → Harness Engineering 的演进。** Prompt engineering 优化单次请求，context engineering 管理每次推理周围的指令、文档、工具定义、历史与记忆，harness engineering 则进一步编排多代理、审批策略、沙箱边界和事件钩子。作者把 Codex CLI 放在后两者的交界处。
3. **可用 Write、Select、Compress、Isolate 四类策略描述 Codex CLI 的上下文工程。** 这四类不是彼此独立的功能清单，而是围绕“什么信息在何时进入哪个窗口、如何留下或退出窗口”的决策框架。
4. **Write：把需要持久存在的知识写到实时窗口之外。** 文中列出三组机制：
   - AGENTS.md 按全局、仓库根目录到当前目录的顺序合并，越靠近当前目录的文件越晚出现，因而具有事实上的覆盖优先级；作者主张把它写成含精确命令、完成标准和测试期望的运行手册，而不是解释背景的 README。
   - 原生 memories 在会话完成后提取持久经验，再全局归并；配置可分别控制生成、使用、外部上下文禁用及限流阈值。
   - Skills 提供可复用的专门指令；PLANS.md 作为会话中持续更新的外部状态，可在压缩后通过重读恢复长期任务连贯性。
5. **Select：在需要时只把相关信息拉入窗口。** 文中把语义化 tool search、MCP `enabled_tools`/`disabled_tools` 范围控制、以及 code mode 中途调用 web search 视为三种选择机制；作者声称 tool search 可把工具定义开销降低 85%–98%，并用 43 工具的 GitHub MCP 服务每轮超过 28,000 tokens 作为不加选择的反例。
6. **Compress：在减少 token 占用时保留任务所需信息。** 自动 compaction 保留最近消息原文并总结更早对话；schema compaction 在压缩大型工具/连接器输入模式时保留 `oneOf`、`allOf` 和更多浅层结构；Goal mode 在预算将尽时用收尾引导、摘要和交接替代直接中断。作者把这三者归为对会话历史、工具模式和会话预算的不同层次压缩。
7. **Isolate：把工作分配到独立上下文边界，防止单一窗口饱和。** 子代理拥有各自的对话历史和工具集；permission profiles 通过能力范围影响可见工具与可接触资源；Seatbelt、Bubblewrap、Landlock 等 OS 沙箱从文件访问层建立硬边界。作者把这些机制分别解释为任务、能力与操作系统级的上下文隔离。
8. **四种策略组合会产生复合效应。** 原文给出四个组合关系：AGENTS.md 可要求先 tool search（Write + Select）；PLANS.md 可在 compaction 后被重读（Write + Compress）；子代理可拥有自己的工具允许列表（Select + Isolate）；不同子代理独立压缩，不互相丢弃上下文（Compress + Isolate）。作者进一步声称，四类策略齐备的团队可在累计输入超过 100,000 tokens 时保持连贯，而未管理的单窗口会话通常在 30,000–40,000 tokens 后退化。
9. **实践清单应同时覆盖四类策略。** 原文建议仓库根目录编写运行手册式 AGENTS.md、启用 memories、限制 MCP 工具、跨多个领域时使用子代理、用遥测监控压缩、并为多文件任务维护 PLANS.md。
10. **最终结论是：上下文窗口有限，工程化管理进入窗口的信息是代理开发中的高杠杆活动。** 作者同时预告 harness engineering 将继续把审批、钩子、执行策略和云端配置等外围脚手架纳入设计对象，并认为这些脚手架可能比提示词或原始上下文本身更重要。

### 关键限制、反例与待核验清单

#### 原文明示的条件与边界

1. **结论具有明确版本快照。** 文章声称映射的是 Codex CLI v0.139 的机制，页面又在 2026-09-10 更新；具体配置项、默认值、GA 状态和行为都可能随版本改变，不能去掉版本条件后写成恒定产品事实。
2. **上下文窗口仍是有限资源。** 四策略并不消除容量上限，只是在持久化、检索、压缩与分区之间管理有限预算；文章结尾明确以“窗口不是无限的”为前提。
3. **记忆并非覆盖所有来源。** 文中配置示例含 `disable_on_external_context = true`，说明 MCP／web-search 等外部上下文线程可被跳过；又明确说 v0.139 起外部工具输出不进入记忆库。因而“跨会话洞见自动累积”不能被理解为会话中的一切事实都会沉淀。
4. **记忆生成受时机与资源条件影响。** 文中描述它在会话空闲后经提取和全局归并运行，并提供 `min_rate_limit_remaining_percent` 的退让配置；这意味着沉淀不是即时、无条件完成的。
5. **压缩必然改变信息形态。** 自动 compaction 只逐字保留较新消息，旧消息被总结；大型 schema 被保留的是更多“浅层结构”，而不是宣称无损保存。文章没有给出如何检测关键信息在总结或 schema 裁剪中丢失的系统方法。
6. **Goal mode 的预算耗尽是软停止而非无限续航。** 它注入收尾引导并产出摘要/交接，不等于任务必然在当前会话完成；如果产物把它画成继续执行或自动完成，会扩大原文主张。
7. **选择与隔离会牺牲可见性。** MCP 允许列表使未选中的工具定义根本不进入窗口；OS 沙箱使边界外文件无法读取。作者把这视为减少噪声和风险的好处，但同一机制也可能让完成任务所需的信息不可达，原文没有提供误删工具或错误划界后的恢复策略。
8. **子代理隔离不代表无需共享接口。** 原文以“前端子代理从不看到后端数据库 schema，反之亦然”说明隔离，但这是理想化示例；涉及前后端契约的任务可能需要经过筛选的共享接口信息。文章未讨论隔离边界过强造成跨域依赖遗漏的反例。
9. **外部检索会扩充上下文，但文章没有讨论来源质量与安全。** code-mode web search 被描述为可在后台并行拉取文档；正文未覆盖检索错误、过期文档、恶意页面、权限或额外 token 成本，因此不能由“可选择”推出“选择结果可靠”。

#### 证据强度与可推广性限制

10. **多个数字结论在正文内缺少实验条件。** 85%–98% 工具定义开销降幅、43 工具超过 28,000 tokens、四策略团队超过 100,000 tokens 仍连贯、未管理会话在 30,000–40,000 tokens 后退化，均由引用支持但正文没有说明模型、任务、样本、测量口径、方差或失败判定。本阶段未读取引用材料，故这些数字只能记录为“作者引用的量化主张”，不能当作已独立验证的普遍阈值。
11. **“三阶段演进”“脚手架更重要”“最高杠杆”属于宏观判断。** 文中给出相关框架和机制例子，但没有在正文中提供足以比较所有开发活动收益的对照实验；这些应标为作者的综合判断，不应写成无争议事实。
12. **“AGENTS.md 作为 README 的团队持续逊于运行手册式团队”缺少正文方法说明。** 原文引了外部文章，但未交代团队样本与“表现”的定义；可保留为实践建议及引用主张，不宜在笔记中升级为严格因果结论。
13. **“跨两个以上领域就用子代理”“永不暴露完整工具目录”等清单项是启发式规则。** 正文没有展示阈值推导，也没有讨论小目录、强耦合任务或子代理协调成本等反例；应呈现为作者建议，而非适用于所有项目的硬性定律。
14. **四策略组合表主要说明机制相容性，尚不足以证明协同增益大小。** 表中的例子能解释两类策略如何一起工作，但正文没有消融实验比较单策略与组合策略，因此“compound”是有机制解释的主张，量化收益仍未充分建立。
15. **框架分类存在边界重叠。** permission profiles 与 OS 沙箱首先是权限/安全边界，作者通过它们改变可见资源与工具来归入上下文隔离；Goal mode 首先是预算和收尾控制，作者将其归为会话级压缩。该映射是解释框架，不意味着这些机制的全部功能都属于上下文工程。

### 完整主线结论

完整阅读可以恢复“问题 → 四种信息操作 → Codex 载体 → 两两组合 → Harness 层持续编排 → 证据边界”的主线。读者第二遍不仅列出机制，还能解释为什么写入与压缩互补、为什么独立子代理不等于安全隔离、为什么量化数字不能作为项目阈值；自测前的四项回答与参考答案一致，说明正文已经提供答题所需知识，答案区没有首次揭示核心机制。

主线仍有一处表达负担：`#compound` 的“保存—发现—瘦身—分界的完整路径”把四个并列操作换成一组新词并排成路径，容易产生线性流程联想，和前文“不是依次执行”形成轻微张力。读者没有发生该误读，因此目前按轻微措辞问题处理；建议沿用“写入—选择—压缩—隔离”的受控词汇，并明确组合是按任务触发而非固定路径。

### 易读性过程证据与独立判断

#### 进入门槛与信息组织

- 标题、副标题和阅读范围在术语展开前交代有限窗口、四类决策与非受控实验边界；读者首屏即形成正确起始认识，进入门槛低。
- `#mechanisms` 在桌面以 `2 × 2` 平行比较，在手机按写入、选择、压缩、隔离单列；每项都有三节点短链、正文解释和代价。读者不需回到原文即可区分四类操作。
- `schema`、`profile`、`OS sandbox` 只给作用级解释，没有技术定义。对于本文“形成框架理解”的目标已足够，进一步实现仍需官方文档，页面也已提醒回查；不是当前重要缺口。

#### 图文配合与阅读连续性

- “写入 ≠ 压缩”“选择 ≠ 隔离”就近消除了最容易发生的概念混淆，读者明确称这是首遍最有用的消歧。
- `#mechanisms` 与 `#compound` 延续同一四类框架，读者能在第二遍补全首遍不清楚的隔离层次和四组协同。
- Harness 工程段一段内引入三个层次及多个构件，读者重读一次，并自行整理成“单次请求 → 每次可见内容 → 运行系统持续执行”。这是可定位的局部密度负担，但没有遮蔽全文结论，按轻微问题处理。可用三个并列短句或小型层级对照降低重读成本。
- 手机组合区四张卡跨多个屏幕，需要记住前一屏内容；标题和“组合关系”框提供了定位，未产生实质误解。正常回读/记忆负担，不单独判失败。

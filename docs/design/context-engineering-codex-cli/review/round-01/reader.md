### 首遍自由复述

Codex CLI 每次推理能直接看到的信息有限。页面建议把上下文管理拆成四种操作：把重要状态写到窗口外以便以后再读；只在当前任务需要时选择资料进入窗口；把当前历史或工具描述压缩成更短表示；让不同任务在独立窗口、工具和权限边界中运行。四项处理的是不同风险，可以配合，但并非固定顺序，也不能单独保证回答正确。

其中有一条连接是我根据图中“写出/按需读入”的相对位置形成的理解：写入保存的外部信息以后可以被选择机制取回。图短说明暗示了这点，但首遍没有具体说明取回由谁触发、何时发生。

### 首遍五问

1. **它讨论什么问题？** 讨论 Codex CLI 如何管理有限的上下文窗口，尤其是哪些信息应外存、何时读入、怎样缩短、以及哪些任务内容不应共享。

### 新增理解

- “写入”的具体价值不只是备份，而是让重要约定、进度摆脱易失会话，在压缩或跨会话后仍可从 `AGENTS.md / memories / PLANS.md` 恢复。代价是外部状态可能过时，写得多也可能更难找。
- “选择”具体由 Tool Search、MCP 工具范围和 Web Search 等在运行时或配置层控制。页面给出的关键区分是：完整信息可以放在外部，但无需每轮全部预装。
- “压缩”包含摘要较早历史、压缩工具 schema，以及在预算将尽时留下交接状态；它缩短当前表示，但可能遗漏精确约定。因此关键状态需要另写到可复核文件，压缩与写入形成互补，而不是二选一。
- “隔离”实际上分三层：Subagents 分开会话历史，profiles 限定能力，OS sandbox 限制资源访问。这解释了首遍中同一卡片里几种手段的差别，也说明“独立上下文”不自动等于安全隔离。
- 四组协同关系把首遍的四个并列动作连成系统：写入×选择是“存全、按需取”；写入×压缩是在摘要后从计划/记忆恢复；选择×隔离是每个子任务只暴露相关工具资料；压缩×隔离是各窗口独立摘要，避免一个任务覆盖另一个任务。
- 页面把提示工程、上下文工程和 Harness 工程分成三个层次：前者优化一次请求，中者管理每次推理能看到什么，后者借权限、沙箱、事件钩子和多代理协调让这些决策持续发生。这里让我第一次看清本文四策略并非完整运行系统的全部。
- 证据分成“可由官方资料核对的机制”和“作者的分析映射/实践经验”。`AGENTS.md` 层级、memories、自动压缩、子代理和工具范围可核对；把它们归入四策略是作者分析。85–98%、30,000–40,000、100,000 token 以及“超过两个领域”等说法缺少统一任务、模型、团队和评价方法，只能作为风险提示或实践清单，不能直接变成阈值。

## 自测原始回答（参考答案展开前已保存）

1. **为什么把完整 MCP 工具目录写进 `AGENTS.md`，不能同时替代“写入”和“选择”？**  写入只表示把信息保存到窗口外，使以后能够读取；选择是当前任务发生时只把相关工具定义和资料读进窗口。把完整目录写入文件完成了保存，却若每轮整份读入反而失去筛选，仍会占用窗口并带来无关噪声，所以不能替代选择。
2. **自动压缩已经存在，为什么多文件长任务仍可能需要外部计划文件？**  自动压缩得到的是当前会话的较短摘要，不保证保留精确约定，也可能跨窗口或跨会话丢失细节。外部计划文件可被检查、更新和重新读取，能保存关键决策、进度与交接状态；但它也可能过时，需要维护。
3. **子代理拥有独立上下文，是否等于它已经获得安全隔离？**  不等于。独立上下文主要把会话历史分开，减少信息串扰；工具能力、权限和文件/系统资源访问仍要由 profiles、权限边界与 OS sandbox 等分别限制。这些层次不是同一种安全保证。
4. **能否把文章的 30,000–40,000 与 100,000 token 数字当作自己项目的可靠切换阈值？**  不能。页面指出这些数字没有统一的任务、模型、团队和评价方法，只适合作为风险提示。自己的切换点需要结合任务耦合度、模型、工具负载、协调成本和实际测量确定。

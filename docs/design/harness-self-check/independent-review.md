### 页面主线原始复述

问题是：Agent 可以写代码后，工程师怎样让它可靠推进交付，而不是每次手工指导。页面主张通过设计环境、约束和反馈，逐步提高自主程度。Harness 在此指围绕 Agent 的工程环境，不是一个单一工具。

三个条件并列支撑 Agent：知识有短入口与结构，才找得到任务依据；规则进入自动检查与违规修正，才反复参与执行；能观察界面、日志和指标，才有依据修正并重新验证。总览中人的节点在环境容器上方，向环境指向；三个机制并排、汇聚到 Agent，避免理解成三个必然时序步骤。下方实现—验证/修正—交付表达任务路径，左侧虚线从持续改进区返回环境，表示将交付暴露的问题沉淀回知识、规则和工具。

边界是人仍决定目标、方向和关键判断；这些是支撑条件而非自动成功保证。报告来自特定团队、空仓库与高吞吐场景，不能直接外推其合并策略；环境本身要维护，长期质量还没有定论。开头明确省略目录布局、工具接线和全部实验数据，需原文时按章节查。

### 不看答案时的四题原始回答

1. 文档多不等于 Agent 在任务时能找到、理解并使用。需要短的稳定入口连接结构化文档、计划和系统结构，把分散知识放入它可读取的环境；数量本身没有解决可发现性和理解成本。
2. 不足够。写在文档里的规范是可读信息，还需把架构与质量边界变成执行中的检查，让违规走修正、重查路径。检查约束边界，而非规定每项实现细节，因此文档与检查互补。
3. 不能确认。完成修改只说明做过实现，没有观察运行结果来发现偏差；缺少观察—修正—再次验证的反馈闭环。要给 Agent 相应运行证据，或由能观察的人/过程验证，再判断可否交付。后半句是我据机制推得的补救方向。
4. 不能。接入 Agent 不是具备完整知识、约束与反馈环境；人仍做目标和关键判断。案例有空仓库、高吞吐等条件，不能推成任意项目适用；环境要持续清理，长期维护质量也仍待观察。

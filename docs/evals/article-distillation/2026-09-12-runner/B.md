## 一、核心结论与主线

**核心结论：** 将调查助手嵌入维修看板，让应用提供当前工单、权限和工具，由执行引擎持续调查并提出建议；涉及写入的建议必须经操作人员批准，只有工具成功返回后才刷新看板，失败不能显示为完成。

**主线合同：** 通用对话框缺少看板选择状态，用户反复说明对象 → 应用提供当前工单、权限及可用工具 → 引擎观察、选工具，资料不足时继续读取并返回判断，能够建议时退出调查 → 应用管理批准规则，由操作人员批准写入 → 批准后更新工单，成功才刷新，失败明确显示失败。

这是对原文工作方式的归纳，不是已经验证的效率提升因果链。接口选择放在主线之后；“单次 / 会话”不能替代对调查、审批与结果处理的理解。

## 二、中文知识笔记内容骨架

### 1. 工作方式：从当前工单调查到可靠呈现执行结果

维修人员通过看板中的设备、工单和历史记录理解现场。通用对话框没有看板当前选择的状态，需要用户反复说明正在处理什么。作者把助手放入看板，由应用直接提供当前工单、权限和可用工具，使调查围绕当前对象开展。

执行引擎负责观察数据和选择工具。资料不足时，它读取更多数据，再回到判断；能够提出建议时，退出调查循环。**退出调查表示形成建议，不表示维修动作已经执行或工单已经完成。** 这句话是依据后续审批和工具结果规则作出的阅读解释。

应用负责界面、数据权限、批准规则与记录。引擎可以提出维修动作，却不能自行批准；操作人员保留写入批准权。

建议涉及写入时，后续流程分成三种可见结果：

- **未批准：** 保留建议，不写入，也不刷新完成状态。
- **批准且工具成功：** 调用工具更新工单，工具成功返回后刷新看板。
- **批准但工具失败：** 显示失败，不把工单显示为完成。

原文只规定工具成功后刷新看板，并未说每次更新都会把工单变为“完成”。不将“刷新看板”改写成“自动完成工单”。不涉及写入的建议在图中停留于建议展示，正文没有进一步规定其执行流程。

### 总图：同一张图连通上下文、调查、批准与执行结果

**读者应看见：** 应用把当前对象交给引擎；引擎可以循环读取资料并形成建议，但必须跨越人的批准关口才能写入；看板结果跟随工具真实返回。

采用“职责分区 + 调查回路 + 条件分支”的单一组合图。分区是职责归属，不是额外执行步骤。最外层为应用容器，边界标题注明“界面 · 数据权限 · 批准规则 · 记录”；内部包含引擎区域、操作人员批准区域，以及工具与看板结果区域。

| 图中位置或结构 | 节点与关系 | 几何表达 |
| --- | --- | --- |
| 顶部输入 | 当前工单、权限、可用工具 → 引擎 | 一组应用输入汇入引擎，连线标“提供” |
| 引擎内部 | 观察与判断 → 资料不足 → 选择工具、读取更多数据 → 返回观察与判断 | 用侧边回路线实际连回判断节点；回路标“补充资料后再判断” |
| 引擎出口 | 可以提出建议 → 建议 | 明确离开引擎循环，连线标“退出调查” |
| 建议之后 | 涉及写入？ | 条件分支；“否”通向“展示建议”；“是”通向操作人员批准节点 |
| 批准关口 | 未批准 → 保留建议 | 独立终点，附“不写入，不刷新完成状态”；无连线通向更新工具 |
| 批准关口 | 已批准 → 工具更新工单 | 只有批准分支进入工具；引擎无绕过此关口的连线 |
| 工具返回 | 成功 → 刷新看板；失败 → 显示失败 | 两条独立路径；失败终点附“不显示为完成”，不与成功终点共用后续箭头 |

箭头表示实际数据提供或执行流转，逐条标明条件；调查回线表示再次判断，不暗示审批失败或工具失败会自动重试。没有原文依据，不增加失败重试、权限升级、自动补偿或工具结果自行审批。

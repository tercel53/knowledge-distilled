## 一、内容骨架

### 核心问题与结论

维修人员原本通过看板中的设备、工单和历史记录理解现场，但通用对话框不知道用户当前选中了什么，用户需要反复说明调查对象。

**核心结论：将调查助手嵌入维修看板，让应用提供当前工单、权限和可用工具，由引擎持续调查并提出建议；涉及写入的建议必须经操作人员批准，且只有工具成功返回后才刷新看板。**

这是一套工作方式的演示。正文没有生产效率或安全性实验数据，不能把嵌入方式或审批设计写成已经证明的提效、安全保证。

### 主线：上下文进入调查，建议经过批准，结果决定展示

1. **应用提供现场上下文，引擎开展调查。** 应用将当前工单、权限及可用工具提供给嵌入的助手。引擎观察数据、选择工具；资料不足时继续读取数据，再返回判断；能够提出建议时退出调查循环。这里的循环属于调查，不是反复请求批准。
2. **调查能力与控制责任分开。** 引擎可以提出维修动作，不能自行批准。应用负责界面、数据权限、批准规则和记录；操作人员负责批准涉及写入的建议。批准规则的归属与批准动作的执行者不能混为一谈。
3. **批准不是写入成功，写入成功才触发看板刷新。** 未批准时保留建议，不写入、不刷新完成状态；批准后调用工具更新工单。工具成功返回后刷新看板；失败则显示失败，不把工单显示为完成。这条结果路径回应开篇：助手接入同一个维修工作环境，也必须让看板展示与工具实际结果保持一致。

以上三点是对正文工作方式的归纳，不是三个独立实施阶段。调查、审批与工具结果必须在同一总览中连接，避免读者自行拼接控制逻辑。

## 四、总览图的语义与几何

**图题：引擎调查并建议，人员批准写入，工具结果决定看板展示。**

### 区域与节点

- 外层“维修看板 / 应用”容器表达宿主环境。容器顶部列出应用责任：界面、数据权限、批准规则、记录；输入区列出当前工单、权限、可用工具。权限是输入与控制边界，不画成引擎可以改变的权限。
- 内部“执行引擎”分区包含“观察数据、选择工具”“判断是否可提出建议”“读取更多数据”“提出建议”。边界旁常显“引擎不能自行批准”。
- “操作人员”分区独立容纳批准判断，不能放在引擎分区内部。
- “更新工具与看板展示”分区容纳工具调用、结果判断与结果节点；与人员分区相邻，便于查看批准后的执行条件。

### 连线与结果路径

| 起点 → 终点 | 线的含义 / 条件 | 几何要求 |
| --- | --- | --- |
| 应用输入 → 引擎 | 提供当前工单、权限、可用工具 | 跨分区输入线，标注“提供” |
| 观察数据、选择工具 → 判断是否可提出建议 | 调查中的判断 | 引擎区内实线 |
| 判断 → 读取更多数据 → 判断 | 资料不足，补充后重新判断 | 真正闭合的回路线，回到判断节点；不能返回批准节点 |
| 判断 → 提出建议 | 可以提出建议，退出调查循环 | 独立出口，与补充资料分支分开 |
| 提出建议 → 操作人员批准判断 | 建议涉及写入时 | 跨分区线，显式写明适用条件；非写入建议留在建议出口，不虚构后续执行 |
| 批准判断 → 保留建议 | 未批准 | 独立终点：“不写入，不刷新完成状态”；不接到工具或成功路径 |
| 批准判断 → 调用工具更新工单 | 已批准 | 唯一进入写入工具的路径 |
| 工具调用 → 工具结果判断 → 刷新看板 | 工具成功返回 | 成功分支直接连接刷新节点，标签不写“自动完成工单” |
| 工具结果判断 → 显示失败 | 工具失败 | 独立终点：“不显示为完成”；没有到刷新节点的连线 |

过程箭头为实线，补充调查回路线可以使用虚线但必须注明“返回判断”。分支使用菱形与条件文字；节点面积不代表工作量或耗时。不同责任区域以标题、边框与位置区分，颜色仅辅助。

### 图旁最小说明

默认显示三句依据，沿图中相同关系排列：

1. P1：通用对话框缺少看板选择状态，嵌入后由应用提供当前工单等信息。
2. P2：资料不足则读取更多数据并返回判断；能够建议时退出，引擎没有批准权。
3. P3：未批准不写入；批准后仍需等待工具成功，失败不能显示完成。

这些说明补充缘由与出处；循环、责任边界和条件分支本身由图形表达。
